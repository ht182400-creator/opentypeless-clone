# Typeless 竞争路线图规格

日期：2026-06-27
仓库：`tover0314-w/opentypeless`
编写背景：在 `v0.1.41` 发布后提出；桌面端 quota 复制改动正在进行中。

## 1. 执行摘要

我们正在把 OpenTypeless 从一个可靠的跨平台 AI 听写工具，打造成一个精致、能在日常工作流中与 Typeless 竞争的语音写作助手。近期目标不是克隆 Typeless 的每一个界面。目标是补齐最高价值的差距：更清晰的基于字数的订阅 UX、更强的听写润色、基于命令的选中文本编辑、Ask Anything 工作流、应用特定的写作行为，以及轻量的个性化，同时保留 OpenTypeless 的开源、BYOK 与隐私优先定位。

推荐路径：

1. **M0：字数配额与清晰度清理**：让订阅 UX 使用 `words/month` 而不是 STT 小时或 LLM tokens，并在首页向已订阅用户展示剩余云字数。
2. **M1：听写对齐**：改善首次体验、首页文案、语言变体、录音限制与润色质量评估。
3. **M2：语音命令与选中文本编辑**：把当前的选中文本上下文提升为一流的 “Speak to edit” 模式，具备可预测的命令行为。
4. **M3：Ask Anything**：增加开放式问答、选中文本问答、可选的搜索动作，以及一个不强迫切换 app 的答案面板。
5. **M4：个性化**：增加用户风格档案、每应用风格规则、自动词典建议与纠错学习。
6. **M5：团队/安全/商业化打磨**：仅在核心工作流令人信赖之后。

## 3. 当前 OpenTypeless 基线

本仓库现有优势：

- 通过 Tauri 的跨平台桌面 app，支持 macOS、Windows、Linux。
- BYOK 优先，外加可选的 Cloud Pro 配额。
- 全局热键、托盘、浮动胶囊、历史、i18n、onboarding。
- 多个 STT provider：Deepgram、AssemblyAI、Volcengine/Doubao、GLM-ASR、Whisper 兼容 provider、云代理。
- 多个 LLM provider 与云 LLM。
- LLM polish prompt 已经能去除填充词、重复、false starts，格式化列表，保留语言，支持词典术语、翻译、选中文本模式与 app 类型附加项。
- macOS 与 Windows 上已有前台 app 检测，把 app 映射为宽泛类型：email、chat、code、document、general。
- 个人词典已有 word 与 pronunciation 字段。
- 选中文本可通过剪贴板哨兵流程捕获并传给 LLM。
- 云订阅状态已暴露：
  - `cloudWordsUsed`
  - `cloudWordsLimit`
  - `cloudWordsResetAt`
  - 遗留的 STT 秒数与 LLM tokens 字段。

与 Typeless 的关键差距：

- 产品文案在某些界面仍泄漏技术配额单位：STT 小时与 LLM tokens。
- 首页当前强调录音与已用配额，而不是“剩余字数”。
- 选中文本模式藏在设置里；它不是清晰的面向用户工作流。
- 没有针对开放式问答的独立 Ask Anything 答案面板。
- 没有命令意图路由器；prompt 处理很多情况，但所有模式共享一个 pipeline。
- 应用特定行为是按类型宽泛的，而不是按 app、按领域或用户可配置。
- 个性化只有手动自定义 prompt；没有学习的风格档案或纠错循环。
- 个人词典是手动的；没有来自重复纠错或失败术语的自动建议。
- 翻译存在，但不是一个拥有自己快捷键与一流心智模型的专用模式。
- 没有内建的“听起来像打出来的而不是转写出来的”质量评估套件。
- Linux 支持是相对 Typeless 的差异化点，但选中文本与应用上下文的对齐在 Linux 桌面环境上更难。

## 4. 产品原则

1. **字数优于 provider 单位**：用户应看到 words/month、剩余字数、重置日期。STT 秒数与 LLM tokens 是实现细节。
2. **就地语音**：产品应在光标或选中文本所在处工作。除非任务需要答案面板，否则避免把用户送到独立编辑器。
3. **命令可预测**：“听写”、“重写选中内容”、“就选中内容提问”、“开放式提问/搜索”在内部应可区分，即便它们共用一个快捷键。
4. **隐私优先的个性化**：风格学习与词典建议默认应为本地存储且可解释。
5. **BYOK 仍是功能而非回退**：Cloud Pro 可以更省心，但 BYOK 应保持可信且可见。
6. **跨平台诚实**：若某个工作流在 Linux/Wayland 上较弱，应清晰展示，而不是假装对齐。

## 5. 用户画像

### 主要：流畅写作者（Flow Writer）

角色：创始人、PM、工程师、学生、创作者或知识工作者，整天都在写。

工作：

- 比打字更快地口述 Slack/邮件/文档/提示词。
- 说出凌乱的想法，收到干净、可发送的文本。
- 无需复制/粘贴就能重写选中文本。
- 把上下文保留在当前 app 内。

痛点：

- 原始听写 awkward、无标点、过于字面。
- ChatGPT 式工作流需要复制/粘贴与切标签。
- 当配额以分钟/tokens 展示时令人困惑。

### 次要：多语言操作者

工作：

- 用一种语言说，用另一种语言输出。
- 自然混用语言。
- 保留专有名词、技术术语、产品术语与地区拼写。

痛点：

- 传统 STT 在混合语言术语与专有名词上失败。
- 翻译常常听起来像翻译而非母语。

### 次要：注重隐私的重度用户

工作：

- 使用自己的 API key 或本地服务。
- 把历史与个性化保留在本地。
- 理解云模式发送并保留了什么。

痛点：

- 商业听写工具对数据处理不透明。
- 仅云工具造成锁定与定价焦虑。

## 6. 成功指标

主要指标：

- 激活率：10 分钟内完成首次成功听写的新用户百分比。
- 重复价值：前 7 天内有 5+ 次听写的活动用户百分比。
- 输出接受率：未被取消、重试或输出后立即手动编辑的会话百分比。首版可用代理指标：30 秒内重复同一字段、手动复制回退，或之后的显式点赞/点踩。
- 云清晰度：已登录云用户中，无需打开 Account 就能识别剩余字数与重置日期的百分比。

次要指标：

- 每 weekly active user 的选中文本命令使用量。
- 新增或被接受的词典术语。
- 翻译模式使用量。
- 从热键释放到最终输出的平均时间。
- 配额耗尽的工单。

护栏：

- 本地 BYOK 设置不退化。
- 核心 BYOK 流程不新增强制云账户。
- 除既有历史设置外，不意外存储选中文本或语音。
- 不破坏 macOS、Windows、Linux 的跨平台发布。

## 7. 范围与分阶段

## M0：字数配额与清晰度清理

状态：当前本地工作中已部分实现。

### 问题

当前桌面文案混用了面向用户的配额概念：

- STT 的 `10h/month`。
- LLM 的 `~5M tokens/month`。
- 云字数字段存在，但不是首页订阅心智模型的主角。

这让 OpenTypeless 显得不如 Typeless 成熟，后者的定价与产品界面都使用字数。

### 要求

- 对已登录且 `cloudWordsLimit > 0` 的订阅用户，首页必须展示：
  - 套餐名
  - 作为首要数字的剩余字数
  - 已用/上限进度条
  - 重置日期（若可用）
- Upgrade/settings 文案在 Cloud Pro 营销中必须避免 STT 小时或 LLM tokens。
- 一旦有精确套餐上限，文案应使用 `words/month` 或 `words/m`。
- Account 与 Upgrade 可以保留详细进度条，但当 `cloudWordsLimit > 0` 时标签应优先云字数。

### 实现备注

当前代码路径：

- `src/lib/api.ts`：`SubscriptionStatus` 已有 `cloudWordsUsed`、`cloudWordsLimit`、`cloudWordsResetAt`。
- `src/stores/authStore.ts`：state 已存储云字数。
- `src/components/HomePage/index.tsx`：在配额条前新增 `RemainingWords` 块。
- `src/i18n/locales/*.json`：新增 `home.wordsRemaining` 与 `home.wordsReset`；更新 Pro 文案。

未来服务端/API 改进：

- 增加套餐元数据端点或扩展 `/api/subscription/status`：

```ts
type SubscriptionStatus = {
  cloudWordsUsed: number
  cloudWordsLimit: number
  cloudWordsResetAt: string | null
  planCloudWordsLimit?: number
  planBillingPeriod?: 'week' | 'month' | 'lifetime'
}
```

这让未订阅用户的升级页能写出如 `200,000 words/m` 这样的精确值，而不是泛泛的 `cloud words/month`。

### 验收标准

- Pro/AppSumo 用户在首页无需打开 Account 就能看到剩余云字数。
- 若用量超过上限，剩余字数额外钳制为 `0`。
- BYOK/免费用户不会看到误导性的付费配额卡片。
- 没有任何 locale 在 Pro 营销界面展示 `10h/month`、`~5M tokens/month` 或等价的技术配额文案。
- 既有 API 测试与构建通过。

## M1：听写对齐基础

### 问题

OpenTypeless 已经会清洗转写，但产品需要一个更锐利的承诺：“自然说，得到读起来像打出来的文本”。Typeless 靠让这个承诺可见且一致而胜出。

### 要求

1. **首页/onboarding 价值主张**
   - 用速度与结果导向的信息替换含糊的 onboarding/首页文本。
   - 建议文案：
     - English: `Speak naturally. OpenTypeless turns your voice into polished text across apps.`
     - 可选速度标签：`Up to 4x faster than typing` 仅当我们对 claim 有把握。
   - 除非在我们的 app 中实测过，否则不要过度宣称精确的 `wpm`。

2. **润色质量评估套件**
   - 增加基于 fixture 的测试：
     - 去除填充词
     - 去除重复
     - 自我纠正
     - 编号列表
     - 项目符号列表
     - 中英混合
     - 邮件 vs 聊天 vs 文档
     - 选中文本指令
   - 把 fixture 存到 `src-tauri/src/llm` 或 `tests/fixtures/polish`。

3. **语言变体**
   - 用变体扩展 `LANGUAGES` 或 STT 配置：
     - English US/UK/AU
     - Spanish ES/MX
     - Portuguese BR/PT
     - 仅当能安全映射到 provider 或 prompt 时才做简体/繁体中文输出偏好。
   - 避免强制字体转换，除非显式选择。

4. **录音限制 UX**
   - 当前 app 在设置里有最大录音时长。仅临近结束才展示剩余时间。
   - 若达到限制，把部分转写存到历史并展示明确状态。

### 验收标准

- 用户在 10 秒内理解首次体验承诺。
- 润色 prompt 测试套件能捕获回归。
- 语言变体选择不破坏既有 `multi` 自动检测。
- 录音超时绝不静默丢失转写内容。

## M2：Speak To Edit 选中文本

### 问题

后端已有选中文本捕获与 prompt 支持，但用户没有把它当作核心功能来感知。Typeless 把选中文本编辑当作 hero 工作流。

### 解决方案

把选中文本编辑做成一流模式：

- 若选中了文本且选中文本上下文已启用，OpenTypeless 把语音输入解释为命令。
- 常见命令：
  - 重写更短/更长
  - 更正式/更随意
  - 修正语法/拼写
  - 翻译选中内容
  - 变成项目符号列表
  - 摘要
  - 解释
- 对编辑命令，就地替换选中文本。
- 对只读/提问命令，展示答案面板而非尝试替换。

### 技术设计

在 LLM prompt 选择前增加意图层：

```ts
type VoiceMode =
  | 'dictate'
  | 'translate'
  | 'edit_selection'
  | 'ask_selection'
  | 'ask_anything'
  | 'search'

type CommandIntent = {
  mode: VoiceMode
  confidence: number
  selectedTextPresent: boolean
  shouldReplaceSelection: boolean
  targetLanguage?: string
  action?: 'rewrite' | 'summarize' | 'explain' | 'translate' | 'draft' | 'search'
}
```

MVP 可用 Rust 或 TypeScript 中的确定性启发式分类：

- 选中文本 + `rewrite`、`make`、`shorten`、`fix`、`translate` 等动词 -> `edit_selection`
- 选中文本 + `summarize`、`explain`、`what does this mean` -> `ask_selection`
- 无选中文本 + `search ... on Google/YouTube/Amazon/GitHub` -> `search`
- 无选中文本 + 开放式问题 -> `ask_anything`
- 默认 -> `dictate`

后续版本可用小型 LLM 分类器，但 v1 确定性规则更安全。

### UI

- Settings > AI Polish：
  - `Selected text commands`
  - `Replace selected text when command edits it`
  - `Show answer panel for read-only answers`
- 胶囊状态：
  - 检测到选中文本：显示小的 “Selection” 提示。
  - 打开答案：显示 “Answer ready” 或打开答案面板。
- History：
  - 存储 mode 与 app 名。
  - 默认避免存储选中文本；仅当用户启用完整上下文历史时才存输出与命令。

### 验收标准

- 选中文本并说 “make this shorter” 会把选中内容替换为更短的文本。
- 选中文本并说 “summarize this” 会打开答案面板或基于显式设置插入摘要。
- 选中文本捕获后剪贴板被恢复。
- 选中文本中的 prompt 注入仍被忽略。
- 在 macOS 与 Windows 上工作。Linux 支持记录为 best effort。

## M3：Ask Anything

### 问题

Typeless 超越听写，变成了系统级语音 AI 助手。OpenTypeless 可以靠增加一个隐私意识的 Ask Anything 模式来竞争，该模式与当前 app 上下文一起工作。

### MVP 范围

Ask Anything v1 支持：

- 通过语音的开放式问题。
- 选中文本问答。
- 起草到活动字段。
- 对显式搜索命令的可选网页搜索动作。

v1 范围外：

- 自主多步浏览。
- 后台 agent。
- 与 Gmail、Slack、Notion API 的深度集成。
- 移动端对齐。

### UX

两类输出：

1. **就地输出**
   - 对起草/重写/翻译命令。
   - 结果进入当前字段或替换选中内容。

2. **答案面板**
   - 对 “explain this”、“what does this mean”、“brainstorm ideas”、“what is...” 式答案。
   - 面板应紧凑、可关闭、可复制，并可选择性地把答案插入活动字段。

### 搜索动作

搜索应显式：

- `search React tutorials on YouTube`
- `search standing desk on Amazon`
- `search this error on Google`

实现：

- 从命令解析目标 provider。
- 通过 Tauri opener 打开 URL。
- 除非命令要求，否则不静默浏览任意页面，也不把选中文本发给搜索。

### 后端/API

对 Cloud 模式，Ask Anything 可能需要托管的 LLM 端点与可选的搜索端点。

BYOK 模式：

- 开放式问题可用配置的 LLM provider。
- 搜索 URL 动作若确定性则不需 LLM。
- 实时网页答案合成应禁用，除非用户配置了支持它的 provider/工具。

### 验收标准

- 用户能从任意 app 问开放式问题并看到弹出答案。
- 用户能在不切标签的情况下就高亮文本提问。
- 用户能插入或复制答案。
- 搜索动作打开正确的 URL。
- 云/BYOK 能力差异可见且不混淆。

## M4：个性化与每应用语气

### 问题

OpenTypeless 当前有：

- 手动词典
- 自定义 polish prompt
- 粗粒度的 app 类型附加项

Typeless 更强的承诺是输出听起来像用户，并按 app 改变语气。

### 解决方案

增加分层风格控制：

1. **全局写作偏好**
   - 既有自定义 polish prompt 变成可见的 “Default style”。
   - 示例：concise、direct、friendly、professional、no emojis、preserve Markdown。

2. **每应用风格档案**
   - 按 app 名与可选的窗口标题/域名的规则档案。
   - 示例：
     - Slack：casual and concise。
     - Gmail/Outlook：professional and complete。
     - VS Code/Cursor：preserve code、prompts、logs、technical terms。
     - Notion/Docs：structured paragraphs and Markdown。

3. **个人词典建议**
   - 从用户重复编辑、被纠错的输出或低置信度转写片段建议术语。
   - 术语进入词典前必须由用户接受。

4. **风格学习**
   - 可选的、从被接受的输与纠错派生的本地档案。
   - 默认本地存储。
   - 仅当显式启用时才云同步。

### 数据模型

SQLite 新增：

```sql
CREATE TABLE app_style_profiles (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  name TEXT NOT NULL,
  app_matcher TEXT NOT NULL,
  window_matcher TEXT,
  tone TEXT NOT NULL DEFAULT 'auto',
  output_format TEXT NOT NULL DEFAULT 'auto',
  custom_prompt TEXT NOT NULL DEFAULT '',
  enabled INTEGER NOT NULL DEFAULT 1,
  created_at TEXT NOT NULL DEFAULT CURRENT_TIMESTAMP,
  updated_at TEXT NOT NULL DEFAULT CURRENT_TIMESTAMP
);

CREATE TABLE dictionary_suggestions (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  word TEXT NOT NULL,
  pronunciation TEXT,
  source TEXT NOT NULL,
  evidence_count INTEGER NOT NULL DEFAULT 1,
  status TEXT NOT NULL DEFAULT 'pending',
  created_at TEXT NOT NULL DEFAULT CURRENT_TIMESTAMP,
  updated_at TEXT NOT NULL DEFAULT CURRENT_TIMESTAMP
```

## 10. 风险与缓解

### 风险：“无限字数”商业上昂贵

Typeless 可以把 Pro 定价为无限。OpenTypeless 当前有一个低价的 Pro 选项。除非成本建模支持，否则我们不应承诺无限。

缓解：

- 对 OpenTypeless Cloud Pro 使用清晰的有限 `xxx words/m`。
- 保留 BYOK 无限作为差异化。
- 显著展示剩余字数。

### 风险：Ask Anything 与隐私优先定位冲突

Ask Anything 可能把选中文本发给云 LLM。

缓解：

- 默认 BYOK 行为保持显式。
- 对选中文本云命令展示首次使用隐私通知。
- 默认不存储选中文本。
- 尽可能增加 local-only 模式。

### 风险：意图路由器做出错误选择

当用户期望答案时却替换了选中文本，是高风险。

缓解：

- 从保守的启发式开始。
- 对模糊命令使用答案面板。
- 增加撤销/复制能力。
- 默认关闭存储原始选中文本的 history 条目。

### 风险：Linux 选中文本对齐难

Wayland 限制全局热键与合成输入。

缓解：

- 对选择命令把 Linux 当作 best effort。
- 在 Wayland 上让剪贴板 copy-only 行为显式。
- 继续提供托盘/app 按钮回退。

### 风险：个性化让人不适

自动风格学习可能惊到用户。

缓解：

- 学习为 opt-in。
- 默认本地存储。
- 清晰的重置/导出控制。
- 用平实语言解释学到了什么。

## 11. 产品讨论的开放问题

1. app 应宣传的精确 Cloud Pro 配额是什么 `xxx words/m`？
2. 我们想直接与 Typeless 的“无限字数”竞争，还是把 OpenTypeless 定位为更低成本的有限云配额 + 无限 BYOK？
3. Ask Anything 应先在仅 BYOK 模式、仅 Cloud 模式，还是两者都可用？
4. 选中文本命令应自动替换文本，还是前几次使用需要预览？
5. OpenTypeless 应增加答案面板，还是把所有答案插入当前字段？
6. 考虑到隐私与实现复杂度，桌面 app 是否要增加网页搜索动作？
7. 个性化 v1 是否应仅本地？
8. 移动端伴侣 app 是否属于竞争目标，还是明确在接下来 2-3 个发布之外？
9. 下一版最重要的语言/变体是哪些？
10. 营销文案应多大胆：“4x faster” vs “speak faster than typing” vs 在 app 内实测的统计？

## 12. 建议的下一次对话

要收敛本规格，按顺序决定这些：

1. **配额定位**：精确的 `words/m`、有限 vs 无限、免费配额。
2. **第一个 hero 工作流**：听写质量、选中文本编辑，还是 Ask Anything。
3. **隐私立场**：云模式可发送/存储什么，以及我们如何清晰披露。
