# TalkMore 云端用量优化实施计划

> **面向智能体执行者：** 必需子技能：使用 superpowers:executing-plans 来逐任务实现本计划。步骤使用复选框（`- [ ]`）语法进行跟踪。

**目标：** 移除空闲订阅轮询，减少账户状态读取，使 Neon 计算资源能够缩容到零，又不让活跃的 STT/LLM/Ask 交互变慢。原子化的托管用量重写保留为未来计划，不属于本次切换范围。

**架构：** TalkMore 仍是鉴权与计费的唯一事实来源。一个只读的账户快照查询替换当前的多查询状态路由。桌面端移除固定轮询，仅在有意义事件时刷新，并在活跃云端录音时并发预热账户路径。通用的数据库原子化 quota 服务仍为后续隔离 PostgreSQL 阶段设计；当前生产环境的 quota 变更保持不变。

**技术栈：** Next.js App Router、TypeScript、Drizzle ORM、PostgreSQL/Neon、Vitest、Rust 2021、Tauri 2、Zustand。

## 全局约束

> **当前范围决策（2026-07-22）：** 负责人当前不新增一个隔离的测试数据库。任务 2 与任务 4–6 暂缓。暂缓的 Drizzle schema 与迁移产物不纳入本次发布，因为遗留的 `select()`/`returning()` 调用否则会隐式引用未应用的列。生产路由继续使用现有计费实现。此暂缓不阻塞状态查询、轮询、预热、录制限制或托管上传工作。

- 在一个从 `origin/main` 创建的隔离 TalkMore worktree 中工作；不要与现有 SEO 分支或脏的 `tests/api-routes.test.ts` 混在一起。
- 保持鉴权行为以及所有遗留响应字段与已发布桌面端客户端兼容。
- 不要把进程内存、Redis、Vercel 缓存或桌面端缓存当作计费权威。
- `/api/subscription/status` 在鉴权后必须是只读的，并只用一次业务数据数据库往返。
- 对于未来的原子化阶段，每次 reserve、settle、release 调用都必须是一次原子化的业务数据数据库往返，并且在重试与并发设备下安全。
- 在鉴权与预留成功之前，绝不发起付费的上游调用。
- 一次失败的生产后使用刷新，或一次失败的未来快照更新，都不得移除已经流式输出/已生成的用户内容。
- 不要新增会让 Neon 保持唤醒的空闲定时器、cron 或后台请求。
- 把现有遗留的 STT 秒数与 LLM token 路径当作兼容计量表，而不是改变当前套餐限额的许可。
