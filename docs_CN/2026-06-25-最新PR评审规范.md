## 3. 最高优先级发现

### P0：#60 可能对 Whisper 兼容的云 STT 静默截断长录音

问题：

#60 把 `src/components/Settings/GeneralPane.tsx` 中的 `max_recording_seconds` 从 `300` 提升到 `3600`，但现有的 Whisper 兼容云 STT provider 仍把缓冲 PCM 限制在约 24MB（16kHz 单声道下约 12.5 分钟）。

相关代码：

1. `src/components/Settings/GeneralPane.tsx`
   - slider 上限现在是 `3600`。
2. `src-tauri/src/stt/whisper_compat.rs`
   - `MAX_AUDIO_BYTES_CLOUD = 24 * 1024 * 1024`。
3. `src-tauri/src/pipeline.rs`
   - `provider.send_audio(&data).await` 的返回值被忽略。

失败模式：

1. 用户把录音时长设为 60 分钟。
2. 用户使用 `openai-whisper`、`groq-whisper`、`glm-asr` 或其他云 Whisper 兼容 provider。
3. provider buffer 达到上限后，`send_audio` 返回错误。
4. Pipeline 忽略了该错误。
5. 录音继续，app 可能保存完整的录音文件。
6. STT 只转写了能放进 provider 内存的那部分。
7. 用户看到一段不完整的转写，却没有明确的错误提示。

为何重要：

这比普通失败更糟，因为它看起来成功了，却丢掉了大部分转录内容。

必需修复：

1. 永远不要忽略 `send_audio` 错误。
2. 增加 provider 限制元数据：
   - 最大上传字节数。
   - 最大录音时长。
   - 是否支持长录音。
3. 在录音开始前，强制取 app 最大时长与 provider 时长中的较小值。
4. 如果会话中途达到 provider 限制，停止录音并向用户展示错误。
5. 如果本地/自定义 Whisper 有意支持更长录音，则要与云 provider 分开处理。

验收标准：

1. 60 分钟录音不能静默产生 12 分钟转写。
2. 云 Whisper provider 展示或强制其上传限制。
3. `send_audio` 失败应被 Rust 测试或 pipeline 级单元测试覆盖。
4. 若用户选择了不兼容的设置，UI 应解释 provider 特定的最大时长。

3. 把 provider 限制更新为与文档一致：
   - 最大文件大小：25MB。
   - 最大时长：10 分钟。
4. 除非已验证，否则不要依赖未文档化的“静音音频免费”行为来做连接测试。

2. `SixtyDbProvider::disconnect` 使用文档化的请求形态。
3. 有效的 60dB key 通过连接测试。

### P1：#60 STT 超时可能产生陈旧/孤儿录音状态

问题：

STT 任务只在 `provider.disconnect()` 返回之后才写录音文件。`wait_for_stt` 在 600 秒后超时，但不会中止或使 STT 任务失效。该任务可能在 `stop()` 已经返回之后才完成并写入录音文件。

相关代码：

1. `src-tauri/src/pipeline.rs`
   - `STT_FINALIZE_TIMEOUT_SECS = 600`
   - `wait_for_stt` 记录超时并继续。
   - STT 任务在 `provider.disconnect()` 之后写录音文件。

失败模式：

1. 用户停止录音。
2. STT provider 卡住或耗时超过超时。
3. `stop()` 返回并可能清理状态。
4. STT 任务最终完成。
5. 它向 app data 写入一个文件。
6. 没有匹配的 history 行被保存，或者陈旧的 `recording_file` 状态被之后的会话消费。

必需修复：

1. STT 超时时，标记该会话为陈旧。
2. 通知 STT 任务中止。
3. 确保陈旧任务不能写 `recording_file`。
4. 把录音的保存与 provider disconnect 解耦，或在 STT 收尾开始前就保存。
5. 使用会话作用域的录音结果，而不是一个共享的 `recording_file` 互斥量。

验收标准：

1. 超时不会留下一个没有 DB 行的文件。
2. 超时不会让陈旧数据影响之后的录音。
3. 超时的 STT 会话有可见的用户侧错误。
4. 超时的已保存录音要么被删除，要么以显式的 `transcription_status = "failed"` 行持久化。

## 4.2 PR #60：Recordings feature

摘要：

这个功能有价值：保存音频、回放、重新转写、删除、限制保存录音数量，都是有用的。但实现尚未就绪，因为它在没有足够护栏的情况下改变了录音时长与持久化语义。

预期用户价值：

1. 保存原始音频供日后审计。
2. 若首个 provider 失败，重新运行转写。
3. 保留转录历史的同时删除音频。
4. 使用压缩存储格式。
5. 避免无界的保存录音数量。

主要架构问题：

该 PR 把录音当作“附加在 history 上的额外数据”，但 pipeline 实际上需要一个会话作用域的录音生命周期：

1. 录音开始。
2. 音频块被采集。
3. 音频被写入或缓冲。
4. 音频被收尾。
5. STT 成功、失败或超时。
6. history 行与录音文件一起提交。
7. 任何失败则运行清理。

该 PR 没有完全建模这些状态。

必需重设计：

### 4.2.1 录音生命周期

增加一个显式的会话作用域生命周期：

```text
capturing -> finalizing_audio -> transcribing -> completed
                              -> transcription_failed
                              -> aborted
                              -> cleanup_failed
```

实现要求：

1. 不要把所有 PCM 都放在一个长生命周期的共享互斥量或全局字段里。
2. 采集期间优先把 PCM 流式写入临时文件。
3. 停止时：
   - 关闭临时 writer。
   - 收尾编码文件。
   - 在一条清晰路径里插入或更新 DB 行。
4. 中止时：
   - 停止采集。
   - 删除临时文件。
   - 不写 history。
5. STT 失败时：
   - 若 `save_recordings` 开启则保留录音。
   - 写入空转写且 `transcription_status = "failed"` 或等价的元数据行。
6. 无语音时：
   - 仅当这是有意的产品行为时才保留录音。
   - 让 UI 明确标注它。
7. 超时时：
   - 中止 STT。
   - 按显式策略保留或删除录音。

数据模型建议：

除了可空文件路径之外，增加录音元数据：

```rust
recording_file: Option<String>
recording_format: Option<String>
recording_bytes: Option<i64>
recording_status: Option<String> // ready, stt_failed, stt_timeout, deleted
recording_provider: Option<String>
```

这样避免从路径猜测格式，并让 UI 解释失败的录音。

### 4.2.2 Provider 限制与长录音行为

要求：

1. 增加 provider 能力元数据：
   - `supports_streaming`
   - `supports_batch_upload`
   - `max_recording_seconds`
   - `max_upload_bytes`
   - `can_retranscribe_saved_file`
2. UI 不应让用户配置所选 provider 无法转写的时长。
3. `send_audio` 错误必须被处理。
4. 若达到 provider 限制：
   - 停止采集或拒绝开始。
   - 发出本地化错误。
   - 仅在策略允许时保留保存的录音。

provider 特定规则：

1. OpenAI/Groq/GLM/SiliconFlow Whisper 兼容云 provider：
   - 强制上传字节上限。
   - 不要静默接受 60 分钟录音。
2. 本地/自定义 Whisper：
   - 若本地服务器支持，可允许更长录音。
   - 仍需要有限的内存/磁盘行为。
3. Deepgram/AssemblyAI streaming：
   - 若后端/provider 支持，可支持更长的实时会话。
   - 保存的文件不应改变流式转写行为。
4. 云 STT：
   - 限制应来自服务端 entitlement/API 行为，而非硬编码猜测。

### 4.2.3 存储清理

要求：

1. `clear_history` 必须删除关联文件。
2. `MAX_HISTORY_ENTRIES` 剪枝必须删除关联文件。
3. `max_saved_recordings` 剪枝必须删除文件并清空 DB 路径。
4. 手动删除录音应保留转录行。
5. app 启动时应删除没有任何 history 行引用的孤儿文件。
6. 文件删除应尽力而为但要记录日志。

建议 helper：

```rust
async fn delete_recording_files(paths: Vec<String>) -> DeleteSummary
```

`DeleteSummary` 应包含：

1. 已删除数量。
2. 缺失数量。
3. 失败路径。

### 4.2.4 Recordings UI 行为

要求：

1. 打开 Recordings 时只获取元数据。
2. 仅播放时加载音频。
3. 不要预加载所有行。
4. 支持分页或增量加载。
5. 展示失败/无语音/超时录音的状态。
6. 当当前 provider 不支持时禁用重新转写。
7. 对不支持重新转写的 provider 显示具体错误。
8. 除非能保证 `format` 非空，否则不要调用 `entry.format.toUpperCase()`。
9. 搜索应大小写不敏感。

推荐 UI 状态：

1. ready。
2. loading audio。
3. playing。
4. audio load failed。
5. re-transcribing。
6. re-transcription unsupported。
7. transcription failed but audio available。

### 4.2.5 重新转写行为

当前行为：

1. 重新转写使用当前的 STT provider，而不是录音时的 provider。
2. 仅支持 Whisper 兼容 provider。
3. UI 让用户在每一行上点击重新转写。

必需行为：

1. UI 应知道当前 provider 是否支持重新转写。
2. 不支持的 provider 应显示明确的禁用状态。
3. 重新转写应更新原始转写。
4. 决定重新转写是否应：
   - 把润色文本更新为原始转写。
   - 重新运行 LLM polish。
   - 在用户重新润色之前保留旧润色文本。
5. 为新转写存储 provider 与时间戳。

推荐 MVP：

1. 重新转写更新 `raw_text`。
2. 仅当 polish 关闭或 UI 标注为“新原始转写”时，才设 `polished_text = raw_text`。
3. 单独新增未来的“重新润色”动作。

## 7. 建议的 PR 评论

### 给 #60 的建议评论

这个功能有用，但我认为现在合并并不安全。最大的问题是长录音正确性：UI 现在允许 3600 秒录音，而 Whisper 兼容云 provider 仍把上传缓冲限制在约 24MB。`provider.send_audio()` 的错误被忽略，所以一个长会话可能静默产生一段部分转写。Recordings 页面还会急切地把最多 200 个完整音频文件载入 JS blob，而 history 清理路径只删 DB 行却不删音频文件。我会围绕会话作用域的录音生命周期、provider 时长限制、懒播放加载以及文件清理测试来拆分或修订它。

### 给 #53 的建议评论

60dB 集成在能可靠工作之前需要一处 API 边界修复。60dB 文档把 multipart 文件字段展示为 `audio`，但该 PR 在连接探测和真实 provider 上传中都发送 `file`。请把它们改为 `audio`，把限制对齐文档化的 25MB/10 分钟上限，并增加 mock/请求形态测试，避免再次退化。

### 给 #52 的建议评论

它指向一个真实缺失的功能，但该分支当前有冲突，应在合并前刷新。重建时请让 PR 聚焦于麦克风选择，并避免无关的 macOS accessibility 变更。一个需要收紧的行为：CPAL 设备名被用作 ID，所以重复或变化的名字需要可见的回退/消歧方案。

### 给 #61 的建议评论

从代码评审看没问题。Requesty base URL 与官方 OpenAI 兼容文档一致，且现有 Rust LLM 工厂已经把所有非云 provider 路由到 OpenAI 兼容 provider。我会用有效 Requesty key 做一次快速连接/润色冒烟测试后合并。
