# 平台发布稳定性规范

日期：2026-06-13
目标发布：v0.1.34 之后的下一个补丁版本，暂定 v0.1.35
状态：已在本地实现，待发布

## 摘要

当前 v0.1.34 之后的高风险问题确实主要集中在 macOS 和 Ubuntu/Linux，Windows 暂时没有新的平台级 blocker。

结论依据如下：

1. Windows：当前 main 的前端测试、类型检查、lint、format 和 build 均通过。Open issues 里唯一明确来自 Windows 的 #50 是 v0.1.27 的 LLM polish 行为问题，main 已经有更强的 prompt 隔离；#51 是 STT/TTS 配置诉求或术语混淆，不是 Windows 平台崩溃。当前不应为了 stale PR 里的 Windows 改动主动重写 Windows 输入链路。
2. Ubuntu/Linux：#48 是 v0.1.34 上明确可复现的 Ubuntu 22.04 MATE/X11 崩溃，日志指向 `xcb_xlib_threads_sequence_lost` 和缺少 `XInitThreads`。这是当前最明确的 release blocker。
3. macOS：#42/#43 都围绕 macOS 选中文本复制、中文输入法、Accessibility 权限、Enigo 主线程兼容性。当前 main 仍在后台线程创建 Enigo 并使用 `AXIsProcessTrustedWithOptions` 请求权限，因此 macOS 仍是高风险区。
4. 跨平台/依赖：#33 无法安装依赖；`npm audit --audit-level=high` 当前仍有 high/critical 前端依赖漏洞。这不是某个平台独有，但会影响 release 质量门禁。

本 spec 的策略是：先修最小平台 blocker，保护 Windows 稳定路径，不直接合并过期/混合 PR；再按独立 PR 处理 Deepgram、依赖审计和非 blocker feature。

## 发布目标

1. 在不改变 Windows 行为的前提下，修复 Ubuntu 22.04 MATE/X11 的启动崩溃。
2. 稳定 macOS 文本捕获/输出与 Accessibility 权限流程，且不把 Linux/Windows 迁到新的输入原语。
3. 保持发布范围聚焦：不合并宽泛的混合 PR、不合并过期的冲突 PR、除非有直接的发布价值否则不并入 feature PR。
4. 在当前账号计费受限的情况下，恢复一条可信赖的发布流水线。
5. 在发布前减少 high/critical 依赖审计发现，或记录任何不可避免的例外。

## 非目标

1. 不在本版本中重新设计 STT provider 架构。
2. 不实现 #28 的摘要 UI。
3. 除非 #51 被确认是关于文本转语音而非本地/自定义语音转文本，否则不新增字面意义的 TTS 支持。
4. 除非出现新的 Windows 专属复现，否则不重写 Windows 键盘钩子或输出。
5. 不把 PR #45 作为整体合并。

### 阶段 2：Ubuntu/Linux X11 崩溃修复

目标文件：

1. `src-tauri/Cargo.toml`
2. `src-tauri/Cargo.lock`
3. `src-tauri/src/lib.rs`
4. `src-tauri/src/linux_x11.rs`（新建的 Linux 专属模块）

要求行为：

1. 仅在 Linux 上，在任何 GTK、WebKit、Tauri builder、窗口、托盘、插件、tracing subscriber 副作用，或 X11/XCB 消费者初始化之前调用 `XInitThreads()`。
2. 使用 Linux 专属依赖（如 `libloading`）动态加载 `libX11.so.6`。
3. 以签名 `unsafe extern "C" fn() -> std::ffi::c_int` 解析 `XInitThreads`。
4. 若库无法加载或符号无法解析，记录 warning 并继续。不要在仅 Wayland 系统或最小化环境硬崩溃。
5. 若 `XInitThreads()` 返回 0，记录 warning 并继续。把它当作降级启动，而非致命。
6. 解析/调用符号后，让加载的 X11 库句柄在进程生命周期内保持存活。
7. 保留现有的 NVIDIA + Wayland DMA-BUF 变通方案，并在 Xlib 线程初始化之后运行它。
8. 不修改 Windows 或 macOS 启动路径。

测试与验证：

1. 在不需要 X11 的测试时，尽可能为 Linux 辅助状态映射增加单元测试。
2. CI：`cargo fmt --check --manifest-path src-tauri/Cargo.toml`。
3. CI：`cargo clippy --manifest-path src-tauri/Cargo.toml -- -D warnings`。
4. CI：`cargo test --manifest-path src-tauri/Cargo.toml`。
5. 手动 Ubuntu 22.04 MATE/X11：从终端启动已安装 app 或 AppImage；确认无 `xcb_xlib_threads_sequence_lost`。
6. 手动 Ubuntu 22.04 MATE/X11：开始/停止录音，确认托盘/菜单仍工作。
7. 手动 Ubuntu Wayland：app 仍应启动；键盘输出可能按现有 Wayland 护栏回退。
8. 手动无 `xdotool` 的 Linux：确认用户可见的回退/warning 仍与之前一致。

验收标准：

1. #48 复现不再在启动时崩溃。
2. Windows 无行为变化。
3. macOS 启动无行为变化。
4. Linux 启动日志显示 Xlib 线程已初始化，或清楚说明为何被跳过。

### 阶段 3：macOS Accessibility 权限稳定性

当前风险：

1. `request_accessibility_permission()` 调用 `AXIsProcessTrustedWithOptions` 并手动构建 CoreFoundation 字典。
2. PR #43 指出该路径在较新 macOS 版本上可能崩溃。
3. 现有实现泄漏 CoreFoundation 对象，并直接使用不安全的 FFI。

要求行为：

1. 保留使用 `AXIsProcessTrusted()` 的 `is_accessibility_trusted()`。
2. 在现有的 `request_accessibility_permission()` Tauri 命令内，用更安全的流程替换提示路径：
   - 检查 `AXIsProcessTrusted()`。
   - 若未授权，使用 `/usr/bin/open x-apple.systempreferences:com.apple.preference.security?Privacy_Accessibility` 打开系统设置到 Accessibility 隐私面板。
   - 返回 `false`，以便前端能显示现有的“需要权限”状态。
3. 除非用正确的 CoreFoundation 所有权安全封装并在受影响的 macOS 版本上测试过，否则不要在发布修复中调用 `AXIsProcessTrustedWithOptions`。
4. 不要在循环中反复请求权限。
5. 保持非 macOS 行为为 `true`。

手动验证：

1. 缺少权限的 macOS：app 打开正确的设置面板且不崩溃。
2. 已授权后的 macOS：`is_accessibility_trusted()` 返回 true 且录音/输出工作。
3. 撤销权限后的 macOS：app 回到“需要权限”状态而不崩溃。

验收标准：

1. macOS 上请求权限期间不崩溃。
2. 用户可通过授予 Accessibility 权限恢复。
3. Linux 和 Windows 权限路径保持不变。

### 阶段 4：macOS 选中文本捕获

当前 main 行为：

1. `capture_selected_text()` 备份剪贴板。
2. 写入一个哨兵值。
3. 在 macOS 用 Enigo 发送 Cmd+C，在其他平台发送 Ctrl+C。
4. 休眠等待剪贴板稳定。
5. 恢复剪贴板并忽略哨兵值。

风险：

1. 在 macOS 上，Enigo Cmd+C 可能与中文输入法冲突或不可靠。
2. PR #42 使用 `osascript`，方向正确，但其合并结果改变了非 mac 行为。

要求行为：

1. 仅在 macOS 上，通过 `/usr/bin/osascript` 发送 Cmd+C：

```applescript
tell application "System Events" to keystroke "c" using command down
```

2. 完全保留哨兵剪贴板保护，与 main 一致。
3. 完全保留剪贴板备份/恢复行为，与 main 一致。
4. 除非复现单独的 platform bug，否则 Windows/Linux 的直接 Enigo Ctrl+C 行为保持不变。
5. 若 `osascript` 失败，记录失败并：
   - 返回 `None`，或
   - 回退到 macOS 专属的 main-thread Enigo 辅助，带确认与超时。
6. 若新增回退辅助，它必须：
   - 报告来自 `run_on_main_thread` 的调度失败，
   - 通过 oneshot 通道发送完成，
   - 有界超时，
   - 绝不无限期阻塞 async 运行时，
   - 绝不 sleep 并假设 main-thread action 已经运行。

手动验证：

1. 英文输入法下的 macOS：选中文本被捕获且剪贴板被恢复。
2. 中文输入法激活下的 macOS：选中文本被捕获且没有插入杂散字符/组字。
3. 无选中文本的 macOS：哨兵被忽略，陈旧剪贴板不被当作上下文。
4. Windows：Ctrl+C 选中文本捕获行为不变。
5. Ubuntu/X11：Ctrl+C 选中文本捕获行为不变。

验收标准：

1. macOS 选中文本捕获变得更可靠。
2. 无 Windows/Linux 选中文本回归。
3. 剪贴板恢复行为保持确定性。

### 阶段 5：macOS 键盘输出主线程安全

当前 main 行为：

1. `KeyboardOutput::type_text()` 使用 `tokio::task::spawn_blocking`。
2. 它在工作线程中创建 `Enigo`。
3. 它分块文本并发送键盘事件。

风险：

1. PR #43 提示在较新 macOS 上 `Enigo::new()` 或 CGEvent 在非主线程可能不安全。
2. 直接把所有平台移到 Tauri 主线程风险太高。
3. 在 async 代码内阻塞于 `std::sync::mpsc::recv()` 可能冻结或饥饿执行。

要求行为：

1. 仅在 macOS 上，把 Enigo 创建与按键/文本事件路由到一个运行在 Tauri 主线程上的辅助。
2. 保留现有的 Windows/Linux `spawn_blocking` 实现。
3. macOS 辅助必须：
   - 显式接受 `AppHandle` 或主线程调度器，
   - 返回结构化的 `Result<(), AppError>`，
   - 确认调度成功/失败，
   - 对调度/完成使用有界超时，
   - 避免在 main-thread 回调期间持有锁，
   - 使用当前的 `TYPE_CHUNK_SIZE` 分块长文本，
   - 保留 Shift+Return 换行行为。
4. 使用最小化的显式上下文设计：
   - 把 `&tauri::AppHandle` 传入 `output::output_with_fallback(...)`，
   - 把同一 handle 传入 `output::create_output(...)`，
   - 让 `KeyboardOutput` 仅在 `#[cfg(target_os = "macos")]` 下 clone/存储 handle，
   - 保持 `ClipboardOutput` 不变。
5. 本版本避免使用全局调度器或单例。

手动验证：

1. macOS 26.5 或受影响版本：键盘输出不再崩溃。
2. macOS：长多行输出以正确的换行被键入。
3. macOS：输出失败通过 `output_with_fallback()` 回退到剪贴板。
4. Windows：键盘输出仍通过现有路径工作。
5. Ubuntu/X11：键盘输出仍通过现有路径工作。

验收标准：

1. macOS 不再为键盘输出在主线程外创建 Enigo。
2. Windows/Linux 代码路径保持不变。
3. 失败回退到剪贴板仍工作。

### 阶段 6：Deepgram 批处理 PR 决策

本阶段对于平台补丁是可选的，除非 Deepgram 截断当前具有发布关键性。

#44 中的已知问题：

1. 批处理 `recv_transcript()` 立即返回 `Ok(None)`。
2. 管线使用 `tokio::select!` 等待 provider。
3. 立即就绪的 `Ok(None)` 分支可能自旋或饥饿真实工作。

若纳入，要求行为：

1. 基于当前 main 变基/重建。
2. 对于文件/批处理 provider，让 `recv_transcript()` 在别处处理上传 finalization 之后永远等待，或等待一个可取消感知的挂起 future。
3. 尽可能复用共享的 WAV 构建逻辑，而不是复制脆弱的音频序列化。
4. 保留 main 的自定义 Whisper 与托管 STT provider 创建行为。
5. 增加一个回归测试，证明批处理 provider 的接收不会热循环。

若纳入，验收标准：

1. Deepgram 不再因流式 finalization 行为而截断。
2. 录音停止后管线 CPU 不飙升。
3. 自定义 Whisper 与其他 STT provider 仍通过现有测试。

### 阶段 8：CI 与发布工作流

当前工作流事实：

1. 发布工作流构建 Windows、macOS arm64、macOS x64 与 Ubuntu 22.04。
2. 发布工作流可由 tag push 或带 tag 输入的 `workflow_dispatch` 触发。
3. 发布工作流使用 `GITHUB_TOKEN`。
4. GitHub 托管的 Actions 计费与仓库所有者/账号/组织绑定，而非仅靠本地 `gh` 登录。

重要计费结论：

仅切换本地 GitHub CLI 账号，若仓库所有者的计费被阻断，无法修复 GitHub 托管的 Actions。要通过 GitHub 托管的 runner 发布，仓库所有者的计费必须健康，或构建必须运行在有可用 Actions 权益的仓库/账号/组织下。

发布路径：

1. 计费修复后的首选路径：
   - 推送最终分支，
   - CI 后合并，
   - 创建 tag `v0.1.35` 或选定的下一版本，
   - 运行 Release 工作流，
   - 验证 draft release 产物，
   - 发布 draft。
2. 计费变通路径：
   - 仅当备用账号有 admin/write 权限且 Actions 可运行的仓库上下文时使用，
   - 仅当对项目的所有权与发布溯源可接受时，才临时转移/fork，
   - 或使用自托管 runner/本地构建，并把产物用具有 `contents:write` 的 token 上传到原始 release。
3. 计费修复后用当前账号重新发布：
   - 不创建同版本的第二 tag，
   - 有意保留或重建同一 tag，
   - 若产物由变通路径构建则删除或替换 draft 产物，
   - 从原始仓库所有者上下文重跑 Release 工作流，
   - 发布前比较产物名、校验和与 app 版本元数据。

发布产物验收标准：

1. Windows 安装器存在。
2. macOS arm64 产物存在。
3. macOS x64 产物存在。
4. Tauri action 期望的 Linux AppImage/deb/rpm 产物存在。
5. About/版本 UI 通过 `VITE_APP_VERSION` 显示发布 tag。
6. `src-tauri/tauri.conf.json`、`package.json`、`src-tauri/Cargo.toml` 由工作流与 tag 版本同步。
