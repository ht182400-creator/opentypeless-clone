# OpenTypeless 项目架构说明

> 面向开发者与原理解释。本文档基于当前仓库源码（`src/` 前端 + `src-tauri/src/` 后端）梳理，覆盖模块划分、三窗口模型、核心管线状态机、STT/LLM provider 抽象、输出层、存储与配置、以及一次完整录音→转写→润色→插入的端到端数据流。
>
> 入门与构建步骤见 `docs/README.md`、中文版 `docs_CN/项目说明README.md`。

---

## 1. 技术栈与定位

OpenTypeless 是商业闭源产品 **Typeless**（typeless.ai）的**开源版**，定位为「AI 语音转文字 + 润色 + 问答」的桌面助手。

| 层 | 技术 |
|---|---|
| 桌面外壳 | **Tauri 2**（WebView2 / WKWebView / WebKitGTK） |
| 前端 | **React 19** + **TypeScript** + **Vite** |
| 状态管理 | **Zustand** |
| 国际化 | **i18next** |
| 后端 | **Rust** |
| 音频采集 | `cpal`（跨平台 PCM 采集） |
| 转写 / 大模型 | 通过 **trait 抽象**接入多家云/本地 provider |
| 输出注入 | `enigo`（跨平台键鼠模拟）+ 剪贴板 |
| 本地存储 | **SQLite**（历史记录 + 词典/纠错规则） |
| 凭据 | 系统凭据保险箱（keyring） |

应用以**三个独立窗口**形态运行，共享同一份前端代码，按 URL hash 分流：

- `#main` —— 主窗口（设置、历史、账户、首页、升级页等）
- `#capsule` —— 悬浮胶囊窗（录音中/转写中的迷你浮窗，常驻屏幕角落）
- `#ask` —— Ask Anything 浮窗（选中文字后召唤的问答便签）

## 3. 前端架构（`src/`）

### 3.1 入口与三窗口路由

- `src/main.tsx`：标准 React 18/19 入口，`createRoot` 渲染 `<App/>`，外层包 `ErrorBoundary`，并引入 `./i18n` 与全局样式。
- `src/App.tsx`：按 `location.hash` 分流到三个根组件（见源码 `CapsuleApp` / `AskApp` / `MainApp`）：
  - `index.html#capsule` → `CapsuleApp` → `<Capsule/>`
  - `index.html#ask` → `AskApp` → `<AskPanel/>`
  - 其它（默认）→ `MainApp` → `MainLayout`（含 `HomePage`/`Settings`/`History`/`AccountPage`/`Onboarding`/`UpgradePage` 等子路由，由 `lib/router.ts` 的 `useRoute()` 再细化）
- 后端在 `lib.rs` 的 `build_ask_window()` 也硬编码了 `tauri::WebviewUrl::App("index.html#ask")`，三者 URL 一一对应（`src-tauri/src/lib.rs:188`）。

### 3.2 状态管理（Zustand）

`src/stores/appStore.ts` 是核心 store，定义了贯穿前后端的关键类型：

```ts
export type PipelineState =
  | 'idle' | 'preparing' | 'recording'
  | 'transcribing' | 'polishing' | 'outputting'
  | 'ask_recording' | 'ask_thinking'
```

该枚举与后端 `pipeline::PipelineState` 严格对应（后端在状态变迁时通过 Tauri 事件向前端广播，前端据此驱动胶囊窗动画与计时）。store 还统一了 `SttProvider` / `LlmProvider` / `OutputMode` / `InsertionStrategy` / `HotkeyMode` / `PolishStyle` 等枚举，是整个 UI 与配置的一致性来源。

`src/stores/authStore.ts` 管理云账户登录态（Better Auth session token），token 会回写后端 `SessionTokenStore` 供云端 provider 使用。

### 3.3 与后端通信（`src/lib/tauri.ts`）

所有 Tauri 命令调用与事件监听都收敛在 `lib/tauri.ts`：

- **命令调用**（invoke）：`getConfig`、`startRecording`、`stopRecording`、`askAnything`、`getHistory`、`getDictionary`、`testSttConnection`、`testLlmConnection` … 对应后端 `#[tauri::command]`。
- **事件监听**：`useTauriEvents` 订阅后端 `emit` 的事件（如 `transcript`、`pipeline-state`、`hotkey:registration-failed`、`tray:settings`），驱动 UI 更新。
- 前端不直接 import 后端代码，全部经由 `@tauri-apps/api` 的 `invoke` / `listen`。

### 3.4 Hooks

- `useRecording`：封装开始/停止录音的生命周期，绑定 `PipelineState`。
- `useTauriEvents`：集中订阅后端事件流。
- `useTheme`：读取配置中的 `Theme`（`light/dark/system`）并应用到 `:root`。
- `useCapsuleResize`：胶囊窗的自动尺寸/位置计算（解决 macOS 隐藏窗口 rAF 暂停问题，见 `App.tsx:54` 注释）。

### 3.5 i18n

`src/i18n/` 下为 i18next 配置 + 多语言 `.json`（10 个语言包）。UI 语言由配置 `ui_language` 决定，启动时在 `CapsuleApp` 的 `useEffect` 中回填（`App.tsx:44`）。

## 4. 后端架构（Rust，`src-tauri/src/`）

### 4.1 装配入口 `run()`（`lib.rs:783`）

`run()` 负责：

1. 注册 Tauri 插件：`tauri_plugin_store`、`tauri_plugin_clipboard_manager`、`tauri_plugin_autostart`、`tauri_plugin_process`、`tauri_plugin_updater`、`tauri_plugin_opener`、`tauri_plugin_single_instance`（处理 `toggle`/`ask` CLI 动作与深链）、`tauri_plugin_deep_link`。
2. `setup` 阶段初始化：
   - 数据目录与 SQLite（`opentypeless.db`，存放历史 + 词典）
   - 全局 `reqwest::Client`（连接池，超时 30s）
   - 应用识别注册表 `AppRegistry` + 用户映射 `UserAppMappingStore` + `ContextDetectorHandle`
   - 核心 `PipelineHandle`（录制管线句柄）
   - 全局快捷键缓存（`HotkeyModeCache` / `AskHotkeyCache` / `HotkeyRoleCache`）、`CloseToTrayCache`、`SessionTokenStore`
   - 注册全局快捷键（`tauri_plugin_global_shortcut`），并启动 `HotkeySupervisor` 后台重试
   - 构建系统托盘菜单（`tray.rs`）
   - 主窗口关闭拦截（close-to-tray）、窗口位置持久化、开机自启同步
3. `invoke_handler` 注册全部 `#[tauri::command]`（见 §4.8）。

### 4.2 核心管线状态机（`pipeline.rs`）

`PipelineHandle` 是系统的「大脑」，状态严格对应前端的 `PipelineState`：

```
Idle → Preparing → Recording → Transcribing → Polishing → Outputting → Idle
                          （Ask 模式另有 ask_recording → ask_thinking 分支）
```

`pipeline.rs` 把各子模块串成一条流水线：

- `audio::AudioCaptureHandle` 采集 PCM（默认 16kHz）
- `stt::SttProvider` 流式转写，回调产出 `TranscriptEvent::{Partial,Final,SpeechStarted,SpeechEnded,Error}`
- 若开启润色/翻译，调用 `llm::LlmProvider::polish`（带 `on_chunk` 流式回调）
- `output` 模块把最终文本注入到当前焦点应用（键盘模拟或剪贴板）
- `app_detector` 提供「当前是哪个 App / 哪种场景（邮件、聊天、代码…）」以决定插入策略与 LLM prompt
- `voice_intent` 判断用户是「听写」还是「下达命令」

关键时序常量见 `pipeline.rs`（如 `SELECTED_TEXT_CAPTURE_DELAY_MS = 60`，用于热键松开后再抓取选中文本）。

### 4.3 音频采集（`audio/`）

- `audio/mod.rs`：定义 `AudioConfig`（采样率等）与 `AudioCaptureHandle` 接口。
- `audio/capture.rs`：基于 `cpal` 的跨平台采集实现，把麦克风 PCM 喂给 STT provider 的 `send_audio()`。

### 4.4 STT provider 抽象（`stt/`）

通过 `trait SttProvider`（`stt/mod.rs:55`）统一接口：

```rust
pub trait SttProvider: Send + Sync {
    async fn connect(&mut self, config: &SttConfig) -> Result<(), AppError>;
    async fn send_audio(&mut self, chunk: &[u8]) -> Result<(), AppError>;
    async fn recv_transcript(&mut self) -> Result<Option<TranscriptEvent>, AppError>;
    async fn disconnect(&mut self) -> Result<Option<String>, AppError>;
    fn name(&self) -> &str;
}
```

`create_provider()`（`stt/mod.rs:71`）按名称工厂化构造，已内置实现（对应 `src/stt/` 子模块）：

| provider 名 | 实现文件 | 说明 |
|---|---|---|
| `cloud` | `cloud.rs` | OpenTypeless 自有云端 STT（默认 API `https://www.opentypeless.com`） |
| `assemblyai` | `assemblyai.rs` | AssemblyAI |
| `deepgram` | `deepgram.rs` | Deepgram |
| `aliyun-qwen3-asr` | `aliyun_qwen3_asr.rs` | 阿里云 Qwen3-ASR（支持国内外区域） |
| `apple-speech` | `apple_speech.rs` | Apple 端侧 Speech（仅 macOS） |
| `volcengine-doubao` | `volcengine.rs` | 火山引擎豆包 |
| `custom-whisper` / 其它 Whisper 兼容 | `whisper_compat.rs` + `config.rs` | 自托管 / OpenAI-Whisper / Groq / SiliconFlow 等（统一 HTTP 上传逻辑） |

`managed_audio.rs` 与 `recording_deadline.rs` 处理「托管上传编码」与「单段录音时长上限」等策略。

### 4.5 LLM provider 抽象（`llm/`）

通过 `trait LlmProvider`（`llm/mod.rs:79`）统一接口：

```rust
pub trait LlmProvider: Send + Sync {
    async fn polish(&self, config: &LlmConfig, req: &PolishRequest, on_chunk: Option<&ChunkCallback>) -> Result<PolishResponse, AppError>;
    fn name(&self) -> &str;
}
```

默认配置（`LlmConfig::default()`，`llm/mod.rs:23`）：`provider = "zhipu"`、`model = "glm-4.7"`、`base_url = https://open.bigmodel.cn/api/paas/v4`。

`create_provider()`（`llm/mod.rs:112`）：`cloud` 走 `CloudLlmProvider`，其余统一走 **OpenAI 兼容**的 `OpenAiProvider`（覆盖 zhipu / deepseek / siliconflow / openai / gemini / moonshot / doubao / qwen / groq / claude / ollama / openrouter 等）。`provider_requires_api_key()` 对 `ollama` 免密钥。

`PolishRequest`（`llm/mod.rs:36`）携带：原始文本、当前 App 上下文摘要 `ContextProfileSummary`、词典、纠错规则 `CorrectionRule`、润色风格、场景 prompt、是否翻译/目标语言、选中文本、语音意图等——这就是「转写结果如何被润色」的全部上下文。

子模块：`cloud.rs`（云端）、`openai.rs`（兼容实现）、`prompt.rs`（prompt 模板）、`context_policy.rs`（上下文策略）、`model_capabilities.rs`（模型能力探测）。

### 4.6 输出注入（`output/`）

- `output/mod.rs`：入口，根据 `InsertionStrategy`（auto / keyboard / clipboardPaste / clipboardCopyOnly / windowsSendInput）选择注入方式。
- `output/keyboard.rs`：基于 `enigo` 的跨平台键鼠模拟。
- `output/clipboard.rs`：`tauri_plugin_clipboard_manager` 剪贴板写入 + 触发粘贴快捷键。
- `output/windows_sendinput.rs` + `windows_modifier_guard.rs`：Windows 下用 `SendInput` 精确控制回车/Shift+Enter/换行，并临时屏蔽修饰键，避免与录音热键冲突。

### 4.7 前台应用识别与场景（`app_detector/`）

- `app_detector/registry.rs`：内置已知 App 列表（邮件/聊天/代码/文档…）。
- `app_detector/user_mappings.rs`：用户自定义「App → 场景/插入策略」映射（持久化）。
- `ContextDetectorHandle`：实时探测当前前台窗口，产出 `ContextProfileSummary`，供 LLM 选择 prompt 与决定注入方式（`auto` 模式据此判断该用键盘还是剪贴板）。

### 4.8 命令层（`commands/`，12 个文件）

所有暴露给前端的 `#[tauri::command]` 集中在 `commands/`，由 `lib.rs:1151` 的 `generate_handler!` 注册：

| 文件 | 职责 |
|---|---|
| `ask.rs` | Ask Anything 问答流程（ask_anything / start_ask_dictation / …） |
| `stt.rs` | STT 诊断、录音能力、连接测试、benchmark |
| `llm.rs` | LLM 连接测试、benchmark、模型能力、拉取模型列表 |
| `config.rs` | 读写配置、自动启动、胶囊自动隐藏、设置 session token |
| `dictionary.rs` | 词典与纠错规则的增删改查、导入导出 |
| `history.rs` | 历史记录读取 / 清空 |
| `credentials.rs` | 系统凭据状态 / 读写 / 迁移 |
| `app_mappings.rs` | App→场景映射的 CRUD 与家族场景分配 |
| `translation.rs` | 翻译目标语言切换 |
| `backup.rs` | 备份数据恢复 |
| `misc.rs` | 辅助：无障碍权限、平台能力、热键注册/暂停/恢复、托盘标签、系统诊断 |

### 4.9 存储与配置（`storage/`）

- `ConfigManager`：基于 `tauri_plugin_store` 的应用配置（热键、润色风格、输出模式、语言…）。
- `HistoryStore`：SQLite 历史记录（转写/问答历史）。
- `DictionaryStore`：SQLite 词典与纠错规则。
- 数据库文件位于应用数据目录 `opentypeless.db`（`lib.rs:856`）。

### 4.10 快捷键与托盘

- `hotkey.rs`：解析配置中的热键为平台快捷键，注册到 `tauri_plugin_global_shortcut`；`HotkeySupervisor` 在注册失败时后台定时重试（emit `hotkey:registration-failed` / `-recovered`）。支持 `hold`（按住录音）与 `toggle`（点按切换）两种模式。
- `native_hotkey.rs`：原生快捷键运行时状态。
- `tray.rs`：系统托盘菜单（显示/隐藏、录音、设置、历史、账户、关于、退出）。

## 5. 端到端数据流（一次「按住说话 → 转写 → 润色 → 插入」）

```
[用户按住全局热键]
   └─ hotkey.rs 捕获 → PipelineHandle.start()
        └─ pipeline.rs: Idle→Preparing→Recording
             ├─ audio::capture (cpal) 采集 PCM(16k)
             ├─ stt::SttProvider.send_audio(chunk)
             │     └─ recv_transcript → TranscriptEvent::Partial/Final
             │            └─ emit("transcript") → 前端胶囊窗实时显示
             ├─ 录音结束 → Transcribing→Polishing
             │     ├─ (可选) llm::polish(raw, context, dictionary, rules, style)
             │     │      └─ on_chunk 流式回传 → 前端实时渲染润色结果
             │     └─ (可选) translation 翻译为目标语言
             ├─ Outputting
             │     ├─ app_detector 判断当前前台 App / 场景
             │     └─ output：keyboard 模拟 或 clipboard 粘贴
             └─ Idle
[用户松开热键] → stop_recording → 文本已进入光标处/剪贴板
```

Ask Anything 分支：`ask.rs::start_ask_flow` → `ask_recording` → 抓取选中文本（`selection.rs`）→ `ask_thinking`（调 LLM 问答）→ 结果在 `#ask` 浮窗展示并可插入。

## 10. 核心模块深入详解：STT / 输出 / 管线

> 本节是对 §4.2（管线）、§4.4（STT）、§4.6（输出）的**实现层深入展开**，所有结论均来自源码（附 `文件:行号`）。建议先看 §4 的接口概览，再读本节的驱动细节。

### 10.1 STT 模块（`src-tauri/src/stt/`）

#### 10.1.1 统一 trait 契约
`trait SttProvider`（`stt/mod.rs:55`）暴露四个方法，所有 provider 共用：

```rust
pub trait SttProvider: Send + Sync {
    async fn connect(&mut self, config: &SttConfig) -> Result<(), AppError>;
    async fn send_audio(&mut self, chunk: &[u8]) -> Result<(), AppError>;
    async fn recv_transcript(&mut self) -> Result<Option<TranscriptEvent>, AppError>;
    async fn disconnect(&mut self) -> Result<Option<String>, AppError>;
    fn name(&self) -> &str;
}
```

`recv_transcript` 返回的是 `TranscriptEvent::{Partial, Final, Error}`（使用时见 `pipeline.rs:1636/1645/1659`）。

工厂 `create_provider(config)`（`stt/mod.rs:71`）按 `stt_config.provider` 字符串分发到 8 个实现：cloud / assemblyai / deepgram / qwen_audio / whisper_compatible / apple_speech / gemini / volcengine，默认 `cloud`（项目自带云端 whisper 服务）。

#### 10.1.2 两种实现范式
- **缓冲上传式（cloud，默认）**：`send_audio`（`cloud.rs:383`）只是把 PCM 帧追加进 `audio_buffer`，上限 `MAX_AUDIO_BYTES ≈ 24MB ≈ 12.5min`（`cloud.rs:27`）；`recv_transcript`（`cloud.rs:404`）直接 `std::future::pending().await`，**不会产出任何事件**；真正的转写发生在 `disconnect()`（`cloud.rs:411`）——把整段音频以 `multipart::Form` 的 `audio` 字段 POST 到 `{api_base_url}/api/proxy/stt`（`cloud.rs:437-463`），并携带 `Authorization: Bearer <api_key>` 与可选 `language`，返回最终文本。即「整段录完 → 一次性上传 → 拿回终稿」。
- **流式 WebSocket 式**（deepgram / assemblyai / gemini 等）：`connect` 时建 WebSocket 连接；`send_audio` 实时推帧；`recv_transcript` 持续 `yield Partial/Final` 事件，前端边录边显。

#### 10.1.3 设计要点
`cloud` 的 `recv_transcript` 永远 pending 也是**合法实现**——管线的 `select`（见 §10.3）会专注在「音频帧」分支，直到 `disconnect` 才拿到文本，管线无需为「缓冲式」写特例分支。两种范式对管线暴露**同一套语义**，差异被完全封装在 provider 内部。

### 10.2 输出模块（`src-tauri/src/output/`）

把最终文本注入到**当前前台应用光标处**，核心是 `InsertionStrategy` 枚举 + 一组插入函数。

#### 10.2.1 五种插入策略
| 策略 | 实现 | 说明 |
|---|---|---|
| `Auto` | `mod.rs` | 自动探测最优路径（键盘 / 剪贴板 / Windows SendInput） |
| `Keyboard` | `keyboard.rs` | 模拟键击逐字输入，含 `check_keyboard_available()` 可用性探测 |
| `ClipboardPaste` | `clipboard.rs` | 写剪贴板后发 `Ctrl+V` 触发粘贴 |
| `WindowsSendInput` | `windows_sendinput.rs` | Windows 专用，调 `SendInput` API 注入；支持中文 IME 与换行模式（`WindowsSendInputOptions` / `WindowsSendInputNewlineMode`） |
| `ClipboardCopyOnly` | `mod.rs` | 只复制不输入——无障碍未授权时的降级 |

#### 10.2.2 配套机制
- **AppDetector**（`app_detector::ContextDetectorHandle` / `TargetAppGuard`）：注入前识别前台应用（浏览器 / Word / VSCode…），决定按键序列与特殊键处理。
- **ModifierGuard**（`windows_modifier_guard.rs`）：注入期间临时屏蔽 / 恢复 Win / Ctrl / Alt，避免把正文误触发成系统快捷键。

#### 10.2.3 无障碍权限边界
`effective_strategy_for_accessibility`（`pipeline.rs:260`）：当 `accessibility_trusted == false` 且策略属于「自动输入」类（Auto / Keyboard / ClipboardPaste / WindowsSendInput）时，强制降级为 `ClipboardCopyOnly` 并返回 `accessibility_required` 错误提示，避免在无权限时静默失败。

#### 10.2.4 注入入口
- 一次性注入：`output::output_with_strategy(...)`（`pipeline.rs:2732`），返回 `InsertStatus::{Inserted, CopiedFallback, ...}`。
- 流式增量注入：`output::output_stream_chunk(...)`（`pipeline.rs:576`），由流式插入 worker 调用（见 §10.3.4）。

### 10.3 管线状态机（`src-tauri/src/pipeline.rs`）

#### 10.3.1 状态枚举（`pipeline.rs:147`）
```
Idle → Preparing → Recording → Transcribing → Polishing → Outputting → Idle
（Ask 模式另有 ask_recording → ask_thinking 分支，对应 #ask 问答浮窗）
```
状态以 `AtomicU8` 跨线程共享（`set_state` 在 `pipeline.rs:934`），前端订阅即可显示进度。

#### 10.3.2 Preparing：音频与 STT 并发就绪
`AudioCaptureHandle::start(config)`（`pipeline.rs:1316`）启动平台音频后端（cpal）；随后 `await_recording_startup(handle.wait_until_ready(), provider.connect(&stt_config))`（`pipeline.rs:1343`）**并发**地等待「音频就绪」与「STT 连接就绪」。注释明确：这样在建立网络连接时录到的语音会被排队，而不是被切掉。任一侧失败 / 超时（30s）→ 回 `Idle` 并报错。

#### 10.3.3 Recording：`tokio::select` 三路循环
录音任务的核心是一个 `tokio::select!`（`pipeline.rs:1558`）：

```rust
tokio::select! {
    _ = stt_control.abort.notified() => break,                 // 用户松手 / 主动中止
    chunk = audio_rx.recv() => provider.send_audio(data),      // 录音帧喂给 provider
    transcript = provider.recv_transcript() => match transcript {
        Ok(Some(TranscriptEvent::Partial(t))) => emit("stt:partial", t),  // 实时中间结果
        Ok(Some(TranscriptEvent::Final(t)))   => { accumulated.push_str(&t); emit("stt:final", accumulated); }
        Ok(Some(TranscriptEvent::Error(e)))   => { emit error; break; }  // 出错即 break，防卡死在 Recording
        _ => {}
    }
}
```

- 音频通道关闭（用户松手）→ 调用 `provider.disconnect()`（`pipeline.rs:1591-1608`）取终稿 → `emit("stt:final")` → 跳出循环。
- `Partial` 事件经 `emit("stt:partial")` 回流前端胶囊窗实时显示。

#### 10.3.4 Transcribing → Polishing → Outputting
- **Transcribing 完成后** → `polish_text(...)`（`pipeline.rs:1926`，耗时报告在 `2545`）调用 LLM provider（默认 `zhipu/glm-4.7`）做润色，产出 `final_text`。
- 流式插入 worker（`spawn_streaming_insert_worker` 在 `pipeline.rs:542`，执行体 `run_streaming_insert_worker` 约 `575`）在 Polishing 阶段就把已确认片段**边出边插**，降低端到端延迟；它经 `output::output_stream_chunk` 注入并汇总 `StreamingInsertReport`。
- **Outputting** 阶段：`output_text(...)`（`pipeline.rs:794`）或 `output_with_strategy`（2732）按 `InsertionStrategy` 注入前台应用，再写 SQLite `HistoryStore` 记录结果与状态。

#### 10.3.5 并发与取消的精妙设计
- `SttTaskControl`（`pipeline.rs:187`）含 `done: Notify` / `abort: Notify` + `id`，配合 `active_session_id: AtomicU64` 与全局 `abort_flag: AtomicBool`。
- `should_finalize_stt_task`（`pipeline.rs:193`）保证**只有当前活跃会话的 STT 结果才被采用**，避免上一次录音的迟到结果污染本次 UI。
- `wait_for_stt`（约 `2000`）用 `control.done.notified()` 等待 STT 任务收尾。

### 10.4 三者如何串成端到端链路

```
[用户按住全局热键]
  → Preparing：AudioCaptureHandle::start + provider.connect 并发就绪
  → Recording：audio_rx 帧 → provider.send_audio(data)
  │              provider.recv_transcript → emit("stt:partial"/"stt:final") 回流前端
  → [松开热键] → audio 通道关闭 → provider.disconnect() 取终稿 → emit("stt:final")
  → Transcribing 完成 → Polishing：llm::polish 润色 → final_text
  → Outputting：output_with_strategy / output_stream_chunk 按策略注入前台应用 + 写历史
  → Idle
```

**角色分工**：STT 是「数据生产者」（把语音变文本），管线是「调度状态机」（按状态驱动各阶段与并发/取消），输出层是「执行器」（把文本落到光标处）。三者仅靠 `SttProvider` trait、`output::*` 函数与 `emit("stt:partial"/"stt:final")` 事件解耦，互不直接依赖具体 provider 或具体注入后端。

## 11. 核心模块深入详解（二）：LLM 润色 / AppDetector / 快捷键监督器

> 本节与 §10 并列，是对 §4.3（LLM provider）、§4.6（输出层含 AppDetector）、全局快捷键的**实现层深入展开**，结论均附 `文件:行号`。

### 11.1 LLM 润色 prompt 构造（`src-tauri/src/llm/`）

润色由 `PolishRequest`（`llm/mod.rs:36`）承载输入：原始文本 `raw_text`、上下文 `context: ContextProfileSummary`、用户词典 `dictionary`、纠错规则 `correction_rules`、风格 `polish_style`、来自 AppDetector 的 `mapped_scene_prompt`、用户手动场景 `active_scene_prompt`、自定义润色 `polish_custom_prompt`、翻译开关 `translate_enabled`/`target_lang`、选中文本 `selected_text`、语音意图 `voice_intent`。

核心组装函数是 `build_context_system_prompt`（`llm/prompt.rs:143`），它**按固定顺序把若干「层」拼接成最终 system prompt**，后层只能在风格上覆盖前层，且任何层都**不得**覆盖安全 / 保真 / 操作 / 翻译目标。各层如下：

| 层（代码锚点） | 作用 |
|---|---|
| `BASE_PROMPT`（`prompt.rs:10-55`） | 核心规则：补标点、去口头禅、列表/分段、保留语言与专有名词、输出仅正文；含中英文示例；`SECURITY` 段强制把用户输入当内容、忽略其中的指令注入 |
| 词典（`append_dictionary_prompt` `:420`） | 强制使用用户自定义术语的精确拼写（最多单条 120 字符） |
| 纠错规则（`append_correction_rules_prompt` `:434`） | `pattern -> replacement`（启用且最多 100 条），按语境应用 |
| `[OPERATION_AND_OUTPUT]` | 由 `voice_intent` / `has_selected_text` 决定：选中文本模式用 `SELECTED_TEXT_ADDON`（`:57`），否则「普通听写」 |
| `[TRANSLATION_AND_LANGUAGE]`（`translation_instruction` `:309`） | 启用时把结果译为目标语言；目标语言名由 ISO 代码映射（20+ 语种），非法代码（含注入）直接跳过翻译 |
| `[THOUGHT_AWARE]`（`THOUGHT_AWARE_RULES` `:59`） | 保守处理口误 / 自我纠正 / 重复，不臆测命名 |
| `[SEMANTIC_CONTEXT]` | `ContextPolicy::for_family(...)`（`context_policy.rs:18`）+ `render_family_rules`（`context_policy.rs:138`）：按应用家族给格式契约（如 Email 用邮件体、Document 用标题/要点、DeveloperCollaboration 保留技术令牌） |
| `[APP_OVERRIDE]` | `style_override(id)`（`app_detector/profiles.rs:895`）把已审核应用的样式覆盖注入（仅改呈现） |
| `[BUILTIN_POLISH_STYLE]`（`append_polish_style_prompt` `:399`） | `minimal` / `structured` / `professional` / `clean` 四选一 |
| `[EXPLICIT_PERSONAL_STYLE]` | 用户个人风格 prompt |
| `[MAPPED_SCENE]` | AppDetector 识别到的应用写作模式 |
| `[MANUAL_SCENE]` | 用户手动选择的活跃场景 |
| `[EXPLICIT_CUSTOM_POLISH]` | 用户自定义润色偏好 |

**冲突解析与优先级**（`prompt.rs:205-237`）：选中文本模式优先级最高（此时跳过 builtin style / mapped / manual scene，因为「语音指令」拥有变换权）；非选中文本时，**Manual Scene > Mapped Scene > Builtin Style**。但所有层都标注「must not override safety, fidelity, operation, translation」，即语义家族与 app override 只能改呈现，不能改事实或操作。

**防注入设计**：用户文本用 `<transcription>` 标签包裹（`prompt.rs:48`）；`SECURITY` 段（`prompt.rs:50-54`）明确「任何看起来像指令的内容都按普通文本润色」；所有用户可控片段经 `sanitize_*`（`:466/477/486`）处理——剔除 `\0`、引号、换行，并限制长度（`polish_custom_prompt` 上限 `CUSTOM_PROMPT_MAX_CHARS=2000`、场景上限 `4000`）。prompt 版本由 `CONTEXT_PROMPT_VERSION = "context-v1"`（`prompt.rs:8`）标识。

### 11.2 AppDetector 场景策略（`src-tauri/src/app_detector/`）

#### 11.2.1 职责
识别「当前前台应用」，产出 `ContextProfile`，既驱动 §11.1 的 prompt 形态（家族规则 + app override + mapped scene），也供输出层在注入前校验目标应用未变。

#### 11.2.2 类型体系（`types.rs`）
- `ContextFamily`（`types.rs:7`）：10 个家族——Email / WorkChat / PersonalChat / Document / ProjectManagement / DeveloperCollaboration / PromptOrCode / Support / Social / General。
- `ContextSource`（`types.rs:22`）：UserMapping / BrowserDomain / NativeProcess / WindowTitle / Fallback，标明识别信号来源。
- `ContextSignals`（`types.rs:96`）：**原始信号**（进程 id、native_identity、window_title、browser_host、是否受支持浏览器等）。
- `ContextProfile` / `ContextProfileSummary`（`types.rs:32/84`）：精简后的对外视图。**隐私边界**：`summary()` 主动剔除 window_title / browser_host / url / confidence / process_id 等原始信号（`mod.rs` 测试 `context_types_serialize_without_raw_signals` 与 `context_types_summary_contains_only_reviewed_metadata` 验证），前端只拿到 `profile_id/family/app_label/icon_key/override_id` 等已审核元数据。
- `TargetAppGuard`（`types.rs:108`）：注入时持有「预期目标进程」，其 `matches`（`types.rs:118`）在输出前确认前台应用没变，避免把文本输错窗口。

#### 11.2.3 内置注册表与分类（`profiles.rs` / `registry.rs`）
- `builtin_profile_definitions()`（`profiles.rs:134`）内置 **70+** 应用画像，每个含 `exact_hosts` / `host_suffixes` / `native_identities` / `process_aliases` / `title_markers` 多维匹配键，并标 `ReleaseTier`（Reference / Extended / Fallback）。
- `AppRegistry::classify(signals)`（`registry.rs`，由 `mod.rs` 测试驱动）把原始信号映射到 `ContextProfile`：**精确 + 边界安全匹配**——已知 host（如 `mail.google.com`→`email.gmail`、`app.slack.com`→`chat.slack`）精确命中；不匹配且不是受支持浏览器时回退 `general.native` / `general.browser`（`mod.rs:64-93` 测试覆盖）。

#### 11.2.4 场景策略三层 + override
- **App override**：`style_override(id)`（`profiles.rs:895`）按 `override_id`（如 `gmail`/`slack`/`github`/`chatgpt`…）返回 `AppStyleOverride`（artifact_kind / formality / density / markup / list_behavior），写入 prompt 的 `[APP_OVERRIDE]`。
- **Mapped scene**：来自 AppDetector 识别到的应用「写作模式」（`RecordingContext.mapped_scene_id`，`types.rs:153`），即 §11.1 的 `mapped_scene_prompt`。
- **Manual scene**：用户手动选的活跃场景（`active_scene_prompt`），优先级高于 mapped / builtin。
- **Personal style**：用户个人风格偏好（`personal_style_prompt`）。

三者与 builtin style 的冲突解决见 §11.1。

### 11.3 快捷键监督器（`src-tauri/src/hotkey.rs`）

#### 11.3.1 角色
全局快捷键注册可能因「被其他程序占用 / 权限不足 / 平台限制」失败。`HotkeySupervisor`（`hotkey.rs:42`）是一个**注册状态机 + 并发守卫**，负责在失败时自愈（有限次快速重试），并防止并发的多次注册尝试互相覆盖状态。

#### 11.3.2 状态机
- `HotkeySupervisorState`（约 `hotkey.rs:23`）：`Starting` / `Installed` / `Failed` / `Disabled`。
- `HotkeySupervisorSnapshot`（`:27`）：对外暴露 `generation` / `state` / `retry_attempts` / `last_error`，供 UI 显示注册健康度。
- 关键方法：
  - `begin_registration_attempt` / `begin_retry_registration_attempt`（`:73`）：后者**仅当** `state==Failed` 且 `retry_attempts ≤ HOTKEY_SUPERVISOR_FAST_RETRY_LIMIT` 才进入 `Starting` 并返回 `generation`，否则返回 `None`（停止自动重试）。
  - `record_registration_success`（`:110`）：置 `Installed`、清零 `retry_attempts`。
  - `record_registration_failure`（`:120`）：置 `Failed`、`retry_attempts += 1`。
  - `next_retry_delay`（`:148`）：`Failed` 且仍在快速重试窗口内时返回 `Duration::from_secs(HOTKEY_SUPERVISOR_RETRY_DELAY_SECS)`，否则 `None`。
  - `wake_for_settings_change`（`:84`）：用户改设置时递增 `generation`、重置重试计数、回到 `Starting`。
  - `disable` / `record_disabled`（`:130/139`）：置 `Disabled`。

#### 11.3.3 generation 并发守卫
`generation` 是一个单调递增代际号。`is_current_generation` / `run_if_current_generation`（`:93/98`）确保**只有「当前代际」的注册任务才能写入状态**——过时任务（例如用户已改设置触发了新代际）的结果会被丢弃。这与管线里 `active_session_id`（`pipeline.rs:193` 的 `should_finalize_stt_task`）是同一思路：用代际/会话号防止陈旧异步结果污染当前状态。

#### 11.3.4 快捷键角色（`HotkeyRole`，`:240`）
六类：`Dictation`（听写主热键）、`Ask`（问答浮窗）、`TranslateSelection`、`EditSelection`、`SwitchScene`、`OpenApp`。`RegisteredGlobalHotkey`（`:263`）记录已注册的 `role` 与其平台绑定。

> 监督循环本身（定时检查 + 调用 `begin_retry_registration_attempt` + `next_retry_delay`）由调用方在独立任务中驱动；supervisor 只负责状态与代际的正确性，不直接 sleep。

## 12. 核心模块深入详解（三）：音频采集 / 存储 / 快捷键底层

> 本节与 §10、§11 并列，是对 §4（总体架构）、§11.3（快捷键监督器）的**更底层展开**：音频如何变成 PCM 帧、配置与历史如何落盘、以及 Fn/RightAlt 这类特殊键如何在操作系统事件层被捕获。结论均附 `文件:行号`。

### 12.1 音频采集（`src-tauri/src/audio/`）

#### 12.1.1 职责与线程模型
`AudioCaptureHandle`（`audio/capture.rs:89`）封装对 cpal 的调用。**关键约束**：`cpal::Stream` 是 `!Send`，必须跑在**专用 OS 线程**（`audio/capture.rs:110` 的 `std::thread::spawn`）。`start()`（`:98`）返回 `(handle, mpsc::Receiver<Vec<u8>>)`——录音帧通过 tokio `mpsc` 通道流出，供管线 `Recording` 状态的 `audio_rx.recv()` 消费。

`AudioConfig`（`capture.rs:60`）默认：`sample_rate=16000`、`channels=1`、`chunk_duration_ms=20`，即每 20ms 凑一帧。

#### 12.1.2 采集与处理流水线（`run_capture`，`:199`）
使用设备的**默认输入配置**（不强制 16kHz mono，`:214` `device.default_input_config()`），在 cpal 回调里按序处理：
1. 算 **RMS 音量**（`(data² 均值).sqrt()`）写 `volume` 供前端音量条显示（`:241`）；
2. `to_mono`（`:188`）：多通道按均值混为单声道；
3. `downsample`（`:166`）：线性插值把设备采样率降到目标 `16000`（`:254`）；
4. f32→**i16 PCM**，累积到 `buffer`，达到 `samples_per_chunk` 即切成帧、转 little-endian 字节后 `sender.try_send(bytes)`（`:271-275`）。

**溢出保护**：`MAX_BUFFER_SAMPLES = 12*1024*1024`（`capture.rs:79`，约 24MB i16 ≈ 12.5min@16kHz mono），达到上限后停止累积，避免内存无限增长（与 §10.1.2 `cloud` provider 的 24MB 上限呼应）。

#### 12.1.3 就绪通知与缓冲深度
- 线程内 `stream.play()` 成功后置 `CaptureState::Recording` 并经 `oneshot` 通道通知 `CaptureReadyAt::now()`（`capture.rs:283-286`）；`wait_until_ready()`（`capture.rs:141`）据此返回，与 `await_recording_startup`（`audio/mod.rs:16`）协同实现「音频就绪 + STT 连好」并发（见 §10.3.2）。
- 通道容量 `AUDIO_CHANNEL_BUFFER_DURATION_MS=60000` → `capacity = 60000/20 = 3000` 帧（`capture.rs:80`），即**约 1 分钟的音频缓冲**；保证在 STT 网络连接期间录到的帧不丢（测试 `audio_queue_preserves_a_minute_while_the_provider_connects` 在 `capture.rs:316` 验证）。

#### 12.1.4 错误处理与测试
- 线程内任何错误 → 置 `CaptureState::Idle` 并经 `startup_notifier.failed(...)` 回报（`capture.rs:118-122`），使 `await_recording_startup` 走 `RecordingStartupError::Audio` 分支回到 `Idle`。
- 测试覆盖（`audio/mod.rs:59` 与 `capture.rs:305`）：音频/STT 并发轮询、启动超时、双错误时 audio 优先、后端未就绪前不报 Recording。

### 12.2 存储层（`src-tauri/src/storage/mod.rs`）

存储分**配置（JSON via tauri_plugin_store）**与**业务数据（SQLite）**两大部分，同文件内（3691 行）。

#### 12.2.1 配置模型与归一化
- `AppConfig`（`storage/mod.rs:331`）聚合所有设置；`TranslationConfig`（`:264`）含 `SUPPORTED_TRANSLATION_LANGUAGES`（20 种，`storage/mod.rs:257`，与 §11.1 翻译目标语言一致）。
- `HotkeyConfig`（`:126`）：每个角色（dictation/ask/translate/edit_selection/switch_scene/open_app）同时保留单值 `*`（兼容旧版）与 `*_bindings` 列表（`MAX_HOTKEY_BINDINGS_PER_ROLE=3`，`:23`）；`normalize()`（`:181`）把旧单值迁移进列表、去重、回填空值。
- `ShortcutBinding`（`:70`）：`primary + modifiers`，`normalize()`（`:100`）做语义去重（`Alt`/`Option` 归一、`Super`/`Command` 归一）、按 `hotkey_modifier_rank` 排序，防重复绑定。
- 场景：`CustomScene`（`:27`，上限 `CUSTOM_SCENES_MAX_COUNT=100`、`SCENE_PROMPT_MAX_CHARS=4000` 与 §11.1 手动场景上限一致）、`ActiveScene`、`FamilySceneAssignment`、`SystemSceneOverride`。

#### 12.2.2 配置持久化（`ConfigManager`，`:1143`）
- 基于 `tauri_plugin_store` 的 `settings.json`（`ConfigManager::load` `:1156` / `save` `:1176`），带 `Mutex<Option<AppConfig>>` 内存缓存避免重复读盘。
- **凭据安全**：`save` 时 `migrate_legacy_config_secrets` 把明文密钥迁移进 `SystemCredentialVault`（macOS Keychain / Windows Credential Manager，`storage/mod.rs:1179`）；`load` 时也会补迁移并持久化（`migrate_legacy_config_secrets_on_load` `:1193`）。这与 §11.1 的「防注入 / 不把密钥放明文」理念一致。

#### 12.2.3 历史记录（`HistoryStore`，`:1295`，SQLite）
- 建表走 **WAL 模式**（`PRAGMA journal_mode=WAL`，`:1302`），`history` 表记录 `raw_text`/`polished_text`/`context_profile_id`/`context_family`/`provider_kind`/`active_scene_*`/`output_status`/`output_error` 等（`:1304`）。
- `add_with_policy`（`:1340`）：先插入、再调用 `prune_with_policy`（`:1403`）按 `max_entries`（钳到 `DEFAULT_HISTORY_MAX_ENTRIES=5000`，`:19`）截断 + 按 `retention_days`（上限 `MAX_HISTORY_RETENTION_DAYS=3650`，`:22`）过期删除。
- **隐私边界**：存入的是 AppDetector 已审核的 `context_profile_id/label/icon_key/family`（`storage/mod.rs:1309-1312`），**不含** window_title / url 等原始信号——与 §11.2 的 `summary()` 剔除隐私信号形成闭环。`HistoryProviderKind`（`:1253`）：ManagedCloud / Byok / Local。
- `restore_backup_data`（`:1500`）：在**单 SQLite 事务**里恢复 history + dictionary + correction（三者同库），避免「部分恢复」破坏本地数据一致性。

#### 12.2.4 词典与纠错（`DictionaryStore`，`:1840`，SQLite）
- 两张表：`dictionary`（word / pronunciation）、`correction_rules`（pattern / replacement / enabled，`storage/mod.rs:1848`）。
- 写入前 `validate_dictionary_text` 校验长度（word/pronunciation 限 100、pattern/replacement 限 120，`:1868`/`:1945`），并按**归一化身份**去重（`dictionary_duplicate` / `correction_duplicate`），与 §11.1 词典/纠错规则上限一致。
- `enabled_correction_rules`（`:2023`）：只取 `enabled=1` 且 `LIMIT 100`——正是 §11.1 prompt 里 `append_correction_rules_prompt` 实际使用的规则集。`MAX_BACKUP_DICTIONARY_ENTRIES=10000`。

### 12.3 快捷键底层：原生键监听（`src-tauri/src/native_hotkey.rs`）

§11.3 的 `HotkeySupervisor` 管理的是「注册状态机 + 代际」，而**真正捕获 Fn / RightAlt 这类需要操作系统事件层的特殊键**的是本文件。编译守卫 `#[cfg(any(target_os="macos", target_os="windows", test))]`（`:1`）表明该原生实现仅在 macOS / Windows / 测试下生效，Linux 走上层 `tauri_plugin_global_shortcut`。

#### 12.3.1 触发类型与组合键模型
`NativeHotkeyTrigger`（`:6`）共 6 种：`Fn` / `Fn+Space` / `Fn+LeftShift` / `RightAlt` / `RightAlt+Space` / `RightAlt+LeftShift`。通过 `base()`（`:29`）/`combo_key()`（`:37`）/`from_base_combo`（`:46`）把「基础键 + 组合键」分解成 `NativeComboState`（`:201`）状态机。

#### 12.3.2 边缘触发（防重复）
`NativeHeldState::edge`（`native_hotkey.rs:86`）用 `AtomicBool::swap` 检测「上升沿（Pressed）/ 下降沿（Released）」，只在状态翻转时产出 `ShortcutState`，避免长按重复触发。`dispatch_native_base_edge`（`:208`）/`dispatch_native_combo_edge`（`:250`）/`dispatch_matching_bindings`（`:176`）协同：基础键按下时若「有待定组合键」先不触发，等组合键到来再触发对应 trigger；基础键单独释放且未用组合时补发 base 的按下+释放。

#### 12.3.3 平台实现
- **macOS（`:275`）**：基于 **CoreGraphics `CGEventTap`**（`SESSION_EVENT_TAP`），监听 `FLAGS_CHANGED`/`KEY_DOWN`/`KEY_UP`；`Fn` 键码 `63`、`FLAG_MASK_SECONDARY_FN=0x0080_0000`（`native_hotkey.rs:329/327`）。**无障碍权限缺失时 `CGEventTapCreate` 返回 null → 明确报错**（`native_hotkey.rs:491`）。启动 3s 超时（`STARTUP_TIMEOUT`，`:288`）。
- **Windows（`:626`）**：基于 **`SetWindowsHookExW(WH_KEYBOARD_LL)` 全局低级键盘钩子**（`native_hotkey.rs:816`）。`RightAlt=VK_RMENU(0xA5)`、`Space=0x20`、`LeftShift=0xA0`（`:654-656`）。回调用 `HOOK_CONTEXT`（`AtomicPtr`，`:658`）取上下文；**默认过滤合成事件**（`LLKHF_INJECTED`），除非设置了环境变量 `OPENTYPELESS_ACCEPT_SYNTHETIC_HOTKEY_EVENTS`（`:648`，用于自测）。同样 3s 启动超时，`Drop` 时 `PostThreadMessageW(WM_QUIT)` 优雅退出（`:744`）。
- 两层通过 `NativeHotkeyRuntime::install`（`native_hotkey.rs:106`）统一出口，上层 `HotkeySupervisor` 在注册失败时经 §11.3 的重试机制自愈。

#### 12.3.4 与 HotkeySupervisor 的分工
| 层 | 文件 | 负责 |
|---|---|---|
| 注册状态机 + 代际守卫 + 重试 | `hotkey.rs`（`HotkeySupervisor`） | 普通全局快捷键的「能不能注册、注册失败自愈」 |
| 原生事件捕获（Fn / RightAlt） | `native_hotkey.rs` | 操作系统事件层的特殊键监听，产出 `NativeHotkeyEvent` |
| 快捷键语义分发 | `hotkey.rs`（`HotkeyRole`） | 把事件映射到 Dictation / Ask / TranslateSelection 等 6 种角色 |

三者关系：原生层产出原始事件 → `HotkeySupervisor` 维护注册健康度并对注册失败重试 → 语义层按 `HotkeyRole` 分发给管线。与 §10.3.5 的 `active_session_id`/代际思路一致，都是「用代际或会话号隔离陈旧异步结果」。
